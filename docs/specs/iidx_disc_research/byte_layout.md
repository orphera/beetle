# 디스크 바이트 배치: 확정, 거의 확정, 의심

PS2 IIDX·pop'n 디스크의 사운드 파일(키음 뱅크, BGM 스트림)과 스테이지 아트 위치에서, 각 필드가 무엇인지 근거의 강도별로 정리한다. 구현 기준은 [wvb.rs](../../../crates/cs-disc/src/wvb.rs), [adpcm.rs](../../../crates/cs-disc/src/adpcm.rs), [iidx.rs](../../../crates/cs-disc/src/iidx.rs)다.

근거 표기:

- **확정**: 디스크 데이터와 측정(길이·파일 끝 표식·vgmstream 비교)이 일치한다.
- **거의 확정**: 여러 곡·디스크에서 일관되게 맞지만, 예외나 직접 검증이 부족하다.
- **의심**: 코드가 그렇게 읽고 있지만 측정이나 재생으로 검증하지 않았다.
- **모름**: 값의 뜻을 찾지 못했다.

---

## 1. 키음 뱅크 (wvb)

파일 하나 안에 헤더 항목, 파일 표, 파일 데이터가 들어 있다.

### 1.1 항목 표: `0x10`부터 `0x8000`까지, 16바이트씩

채보의 소리 번호 `n`(1부터)은 `0x10 + (n-1)*16`의 항목이다.

| 오프셋 | 크기 | 필드 | 근거 |
| --- | --- | --- | --- |
| +0 | u16 | 채널: `0xff00` 모노, `0x0000` 왼쪽, `0x0100` 오른쪽 | 거의 확정. 왼쪽 항목 뒤에 오른쪽 항목이 오면 스테레오로 묶는다(DXY!, GEKKO 등). |
| +2 | u16 | 종류: `0` 미사용, `1` 팬 사용, `2` 저장된 대로 재생 | 거의 확정. 측정에서 `0x0200`이 주로 나오고, 그때 +8/+9는 `1`, `127`이다. |
| +4 | u32 | 길이(ms) | **확정.** 샘플 수 ÷ 길이로 얻은 레이트가 대부분 0.1% 안에서 표의 값과 맞는다. |
| +8 | u8 | 팬(종류 1에서만 사용) | 거의 확정. 종류 1에서 +8과 +9가 같은 값이다. |
| +9 | u8 | 팬 (+8과 같은 값) | 거의 확정. 같은 값만 확인했다. |
| +10 | u16 | 파일 번호 | **확정.** 소리마다 파일 번호가 1씩 늘어나고, 파일 표의 범위 안에 든다. |
| +12 | u8 | 볼륨(0–127) | **의심.** 값 범위는 0–127이지만, 선형 게인인지 모른다. 아래 3절 참고. |
| +13–15 | - | 미확인 | **모름.** 관측된 항목에서 0이다. |

*길이 0*인 항목은 파일이 있어도 소리로 쓰지 않는다. IIDX 10에서 길이 0 항목이 47개 있고, 파일 번호 0에 몰려 있다. 빈 자리로 보인다(거의 확정).

### 1.2 파일 표: `0x8000`

| 오프셋 | 크기 | 필드 | 근거 |
| --- | --- | --- | --- |
| +0 | u32 | 파일 수 | **확정.** 레코드 개수와 파일 끝 위치가 맞는다. |
| +4 | u32 | 미확인 | **모름.** 0으로 보인다. |
| +8 | u32 | 스크램블 플래그(0이 아니면 키로 해제) | **의심.** 코드는 이 값을 읽지만, 디스크별 값과 재생 결과를 모두 확인하지 않았다. |

### 1.3 파일 레코드: `0x8010`부터, 파일 수만큼 16바이트씩

데이터 시작점은 `base = 0x8010 + 파일수*16`이다. 파일 `i`의 바이트는 `base + offset[i]`에서 `size[i]`만큼이다.

| 오프셋 | 크기 | 필드 | 근거 |
| --- | --- | --- | --- |
| +0 | u32 | 파일 오프셋(`base` 기준) | **확정.** 한 뱅크(521개 파일)에서 파일 끝 표식이 `size`와 맞았다. 파일끼리는 연속되지 않는다(섹터 정렬이나 빈 간격이 있다). |
| +4 | u32 | 파일 크기 | **확정.** 같은 검사에서 확인했다. |
| +8 | u16 | 미확인 | **모름.** 대부분 `1`로 보인다. |
| +10 | u16 | 레이트 코드(상위 바이트) | 거의 확정. 아래 1.4 참고. |
| +12 | u32 | 미확인 | **모름.** 0으로 보인다. |

### 1.4 샘플 레이트

파일 레코드의 레이트 코드를 표(`wvb.rs`의 `rate`)로 바꾼다. 표 값은 "Thanks Konami"라는 출처를 따랐고, 측정으로 다음이 드러났다.

- **확정**: 44100, 32000, 22050, 16000, 24000, 20000, 18000, 12000, 40000, 48000(코드 `0x3c`, 측정 48016) 등 측정과 맞는 코드가 많다.
- **의심 → 대체**: 같은 코드라도 디스크마다 실제 레이트가 다르다. 예를 들어 코드 `0x41`은 IIDX 10에서 37000에 맞지만, IIDX 12와 16에서는 약 38000이고, pop'n 14에서는 약 36000이다. 코드 `0x43`은 pop'n 13에서 약 33000, 표의 34000과 3% 어긋난다.
- **현재 처리**: 길이가 0이 아니면 샘플 수 ÷ 길이로 레이트를 얻는다(`measured_rate`, 커밋 `02ea131`, `d1d3caf`). 표는 길이가 0이거나 8–96kHz 밖일 때만 쓴다. 라멘토(pop'n 13)가 이 처리로 맞아졌다고 확인했다.
- **남은 의심**: 길이가 짧은 소리(수십 ms)는 ms 반올림 때문에 오차가 커질 수 있다. 실제 청취로는 확인하지 못했다.

## 2. ADPCM 프레임

PS2 SPU ADPCM. 16바이트에 28샘플이다.

| 바이트 | 뜻 | 근거 |
| --- | --- | --- |
| 0 | 상위 4비트: 예측기(0–4 사용), 하위 4비트: 시프트(12 초과는 9로 읽음) | **확정.** vgmstream과 샘플 단위로 맞춘 결과다(`sound_check`). |
| 1 | 플래그: `1`·`3`은 루프, `7`은 끝 | **확정.** 끝 표식이 파일 끝에 놓인다. |
| 2–15 | 4비트 샘플 14바이트, 하위 니블부터 | **확정.** |

### 2.1 스크램블

스크램블된 뱅크는 프레임마다 바이트 0을 `^0xff`, 바이트 1–3을 키만큼 뺀다.

| 키 | 값 | 근거 |
| --- | --- | --- |
| 키음(14–16) | `[0, 0xdc, 0]` | **확정.** vgmstream과 샘플 단위로 일치했다. |
| RED 키음 | `[0xfe, 0xef, 0x37]` | **거의 확정.** 파일 끝 프레임 `ff 05 66 ae`로 판별한다. |
| BGM | `[0, 0xfe, 0]` | **확정.** |
| 10·11·12·13 키음 | 미확인 | **모름.** 이 디스크들의 뱅크는 같은 키로 읽힌다(소리가 난다). 키가 맞는지는 파일 끝 프레임으로 간접 확인했을 뿐이다. |

## 3. BGM 스트림

0x800바이트 헤더, 그다음 ADPCM 프레임이 채널별로 16바이트씩 번갈아 든다.

| 오프셋 | 크기 | 필드 | 근거 |
| --- | --- | --- | --- |
| 8 | u32 | 데이터 시작 | **확정.** |
| 12 | u32 | 데이터 크기 | **확정.** |
| 24 | u32 | 레이트 | **거의 확정.** 거의 모든 BGM이 44100이고, IIDX 16에서 하나만 48000이다(그 곡은 헤더를 그대로 따른다). |
| 28 | u32 | 채널 수 | **확정.** 대부분 2다. |
| 32 | u32 | 스크램블 플래그 | 거의 확정. 모든 측정 곡이 0이다. |
| 36 | u32 | 인터리브(16만 지원) | **확정.** |
| 40 | u32 | 볼륨 | **의심.** 아래 3.1 참고. |

### 3.1 볼륨(40번)

- 값 범위는 디스크마다 다르다(IIDX 10: 29–127, IIDX 12: 18–115, IIDX 13: 1–98, pop'n 14: 60–127).
- 값 1은 길이 0.8초짜리 무음 더미 스트림에만 나온다. 실제 곡에는 없다. 그래서 "1을 곱하면 무음이라 gain이 아니다"라는 근거는 쓸 수 없다.
- **현재 처리**: 볼륨을 적용하지 않고 풀 레벨로 재생한다. XENON(값 48)에서 만족을 확인했다(`36cc63d`). 이 처리는 다른 곡들에도 같이 적용되므로, 낮은 값의 곡이 커진다.
- **모름**: 이 값이 선형 게인인지, 디스크 기준 레벨인지, 게임이 무시하는지 판별하지 못했다.

## 4. 소리 번호 대응(채보 → 뱅크)

- **확정**: 채보의 `NNNN.wav`에서 `NNNN`이 뱅크 항목 번호다(`sound_number`). 1번은 IIDX에서 BGM 큐이고, pop'n에서는 1294번이 BGM 큐다.
- **의심 → 확인 실패**: 다른 번호 대응(한 칸 밀림)을 시험했다. HAPPY SKY에 한 칸 보정을 적용해 본 결과가 틀렸다고 확인되어 되돌렸다(`52d1ba6`). 드르륵 구간의 소리는 아직 찾지 못했다.

## 5. 무음 키음

디스크 데이터가 전부 0인 키음이 있다.

| 디스크 | 키음 수 | 무음 | 특징 |
| --- | --- | --- | --- |
| IIDX 12 HAPPY SKY | 30,769 | 181 | 길이 159ms가 64개로 몰려 있다. |
| IIDX 10 | 25,009 | 77 | 길이 0이 47개, 파일 번호 0에 몰린다. |
| pop'n 13 | 44,346 | 5 | - |

- **확정**: 무음인 파일도 구조는 정상이다. 프레임 헤더(`0c` 등)와 끝 표식이 맞고, 데이터만 0이다.
- **확정**: PCSX2로 같은 ISO를 돌려도 airflow 드르륵 구간(15번), INSTRUMENTAL 드르륵 구간(7번)이 무음이다.
- **의심**: AC나 유튜브 CS 영상에서 소리가 나는 것을 보면, 가진 ISO와 그 영상의 데이터(리비전, 덤프)가 다를 수 있다. 덤프 해시와 판본을 확인하지 않았다.
- **두 드르륵 소리의 공통점**: 길이 255ms, 파일 번호 6, 종류 2. 우연인지 구조인지 확인하지 않았다.

## 7. 측정 방법 (재현)

이 기록의 수치는 임시 진단 예제로 얻었다(예제 파일은 저장소에 두지 않았다). 같은 방법으로 다시 확인할 수 있다.

1. 디스크 이미지를 `cs_disc::SectorReader::open_image`로 열고, `Disc::open`으로 곡 목록을 얻는다.
2. 곡의 `sound_files`로 뱅크 파일 번호를 얻고, `read_file`로 바이트를 읽는다.
3. 항목의 길이(+4)와 `decode_file`의 샘플 수로 레이트를 계산한다.
4. 무음은 `decode(n)`의 모든 샘플이 0인지로 판별한다.
5. BGM 헤더는 `read_file` 결과의 40·24번 바이트를 읽는다.

검증 기준:

- 레이트 검증: 샘플 수 ÷ 길이가 표의 값과 0.1% 안에서 맞는지.
- 재생 검증: 같은 소리를 vgmstream으로 디코딩해 샘플 단위로 비교(`sound_check` 예제 방식, vgmstream 실행 파일 필요).
- 청취 검증: 영상의 특정 시각에서 해당 소리가 나는지 확인.

## 8. 아직 답하지 못한 질문

1. 드르륵 구간의 소리는 디스크 어디에 있는가? 무음이라면, 영상의 소리는 다른 데이터에서 나온 것인가?
2. BGM 볼륨(40번)은 게임에서 어떤 척도인가?
3. 항목 +13–15, 파일 표 +4, 레코드 +8, +12는 무슨 값인가?
4. 10–13 디스크의 키음 키(스크램블)는 14–16과 같은가?
5. 사용 중인 ISO가 영상의 판본과 같은가? 덤프 해시로 확인이 필요하다.
