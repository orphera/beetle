# BPM 컬렉션 관리 리디자인 설계 (2026-10-09)

BPM(`bms-package-manager`의 `bpm` CLI)과 `bpm-gui`를 "BMS 컬렉션을 관리하는 도구"로 다시 잡는다. 순서는 CLI 먼저, GUI는 CLI 위에서 나중에 한다. 구현 전 설계다.

## 1. 출발점: 사용자가 겪은 문제

BMSeeker를 쓰지 않고 손으로 정리하면서 겪은 문제다.

| # | 문제 | 원인 (현재 구조) |
|---|---|---|
| P1 | 중복 BMS를 찾을 수 없다 | 식별자가 없었다. 같은 파일이 폴더와 패키지에 따로 있어도 서로 모른다. |
| P2 | 분류 기준을 잡기 어렵다 | 한 폴더에 몰아넣거나, 폴더를 나누자니 기준이 없다. 분류가 물리 위치에만 묶여 있다. |
| P3 | 차분(같은 곡의 난이도별 차트)이 흩어진다 | 차트 단위 정보는 있지만 "같은 곡의 차분 묶음"이 없다. 차분마다 다른 폴더, 패키지 설치본과 폴더 본이 따로 놀아 상태를 한눈에 알 수 없다. |
| P4 | 패키지와 폴더의 관계가 불분명하다 | 패키지 설치 저장소(`packages/`)와 기존 폴더(`library.dat`)가 두 개의 목록이다. |

## 2. 이미 있는 기반

이 설계는 새 개념을 처음부터 만드는 것이 아니라 아래 기반 위에 쌓는다.

- **차트 식별자**: `ChartId`(SHA-256, 파일 바이트 기준)와 MD5 별칭이 [`crates/beetle-core/src/identity.rs`](../../crates/beetle-core/src/identity.rs)에 있다. [chart identity 설계](2026-10-08-chart-identity-design.md)에서 확정했다. P1의 핵심 재료다.
- **기존 컬렉션 경로**: `bpm library add|list|remove`가 기존 폴더를 복사 없이 등록한다(`library.dat`). 제품 전략의 "Existing Collection First"와 맞는다.
- **곡 단위 묶음 힌트**: 최근 커밋에서 폴더의 제목과 아티스트를 차트들의 다수결로 정하도록 했다. P3의 "곡" 묶음 기준으로 재사용한다.
- **난이도표**: [difficulty table 설계](2026-10-08-difficulty-table-design.md)는 표의 MD5/SHA-256과 내 차트를 맞춘다. 이 매칭이 "차분 묶음"과 "분류"에도 쓰인다.
- **패키지**: `packages/<id>/<state_hash>/package.bmsp`에 설치된다. 패키지 안 차트도 같은 바이트 기준 `ChartId`를 가진다.

## 3. 핵심 모델

물리 위치와 논리 구조를 분리한다. 파일을 어디에 두는지와, 무엇인지 아는 것은 별개다.

```text
Chart    ChartId 하나. 바이트가 같으면 같은 Chart.
         └ Location*  Chart가 실제로 있는 곳 (폴더 경로 또는 패키지 state). 여러 개 가능.
Song     같은 곡의 차분들의 묶음. Chart를 여러 개 가진다.
Collection  사용자가 등록한 출처 (library 폴더, 설치된 패키지).
Table    난이도표. Chart와 MD5/SHA-256으로 연결된다.
```

- **Chart**는 식별자로 정의한다. `Location`은 여러 개일 수 있고, 같은 `ChartId`의 위치가 둘이면 중복이다.
- **Song**은 물리 폴더가 아니라 논리 묶음이다. 묶는 기준은 아래 우선순위다 (Opus 검토 결과, [§3.1](#31-song-묶음-기준-검토-결과)에 근거 정리).
  0. 사용자가 명시적으로 지정한 묶음 (`bpm song link|unlink`, ChartId 목록으로 저장. "묶지 말 것" 쌍도 저장)
  1. 같은 폴더 또는 같은 패키지 안의 차트들. 제목 키로 먼저 나누고, 한 키가 과반이면 그 폴더를 한 곡으로 본다. 과반이 없으면 여러 곡을 몰아넣은 폴더로 보고 키별로 나눈다.
  2. 같은 `ChartId`가 여러 묶음에 있으면 묶음을 합친다(union-find). 한 차트는 한 곡에만 속한다.
  3. 폴더 사이 묶기. 제목 키, 아티스트 기본 키, 키음 겹침(`#WAV` 파일 이름 집합 Jaccard ≥ 0.5 또는 포함 관계)이 모두 맞을 때만 자동으로 묶는다. 제목과 아티스트만 같으면 "같은 제목의 다른 곡일 수 있음"으로 후보만 보여준다.
- **분류**(P2)는 물리 위치가 아니라 **질의와 태그**다. 모드(5K/7K/…), 난이도표 레벨, 패키지 여부, BGA 유무, 중복 여부 같은 속성으로 목록을 필터링한다. 사용자는 폴더 구조를 설계하지 않아도 된다.
- **`ContentKey`**(의미상 같은 차트, 재인코딩·오타 수정)는 이 설계에서 구현하지 않는다. [chart identity 설계](2026-10-08-chart-identity-design.md)의 결정을 따른다.

## 4. 문제별 해결

### P1 중복

- `bpm scan`이 등록된 출처(library 폴더와 설치 패키지)를 훑어 `ChartId`별로 묶는다.
- `bpm dupes`는 같은 `ChartId`가 둘 이상 있는 그룹을 보여준다. 각 위치에 출처(폴더 또는 패키지 state)를 붙인다.
- 같은 곡의 다른 바이트 차트(`ContentKey` 없이는 판별 불가)는 이번 범위가 아니다. `dupes`는 **바이트 동일 중복만** 보고한다. 이 한계를 출력에 명시한다.
- **삭제는 사용자가 요청할 때만, 하나씩, 어렵게** 한다. 도구가 먼저 삭제하거나 일괄 정리하는 명령은 두지 않는다.
  - 삭제 명령은 `bpm delete <경로 또는 ChartId>` 형태로 한 번에 한 항목만 받는다. 여러 항목을 한 줄에 받는 옵션은 두지 않는다.
  - 실행하면 대상의 전체 경로, `ChartId`, 같은 바이트 사본의 개수, 남게 되는 사본을 보여주고, 대상 `ChartId`의 앞 16자리를 직접 다시 입력해야 진행한다(확인 문자열 입력).
  - 패키지 안 차트는 패키지 state 자체를 지우는 것이므로 `bpm uninstall`로만 가능하고, `bpm delete`로는 지우지 않는다.
  - 삭제 전 해당 파일을 휴지통 또는 `trash/` 폴더로 옮기는 것을 기본으로 한다. 완전 삭제는 `--purge`를 명시해야 하며, 이 옵션도 확인 문자열을 요구한다.
  - 이번 단계는 목록 출력(`bpm dupes`)까지만 구현하고, `bpm delete`는 후속 단계로 둔다.

### P2 분류

- `bpm songs [필터]`와 `bpm charts [필터]`로 질의한다. 필터 예시: `--mode 7k`, `--table sl --level 3`, `--packaged`, `--unpackaged`, `--dupes`, `--bga`.
- 필터는 하나의 작은 문법으로 통일한다(`key=value`를 여러 개 받는다). 정규식 크레이트는 금지이므로 단순 비교만 지원한다.

### P3 차분

- `bpm songs`는 Song 단위로 보여준다. 한 곡 아래에 차분 목록(난이도, 모드, 위치, 패키지 여부)이 붙는다.
- `bpm song <id|제목>`은 한 곡의 차분 전부를 보여준다. 차분 중 어느 것이 어디에 있는지, 설치본과 폴더 본이 어떻게 다른지 한 화면에 나온다.
- 같은 곡이 여러 위치에 있어도 **대표 위치를 두지 않는다.** 위치 목록을 결정론적 순서로 보여주고, 공통 값은 한 번만, 위치마다 다른 값만 표시한다 (아래 P4의 병합 표시 참고).

### P4 패키지와 폴더

- 패키지 설치본과 폴더 본을 같은 `ChartId`로 연결한다. 연결된 Chart는 "패키지 설치됨 + 폴더 있음" 같은 상태로 보인다.
- **병합 표시 (기본 동작, 대표 위치 없음)**: 같은 `ChartId`는 바이트가 같으므로 파싱 값(제목, 레벨, 모드, 노트 수, BPM, MD5, 난이도표 소속, 점수)은 충돌하지 않는다. 충돌할 수 있는 것은 위치에 딸린 값뿐이다: 파일 이름, 리소스 상태(키음·BGA 존재), 패키지 manifest의 제목·버전, 폴더 이름, 수정 시각.
  - 공통 필드는 한 번만 보여준다.
  - 위치 목록은 종류(폴더, 패키지) → 경로 또는 패키지 ID → 버전 순의 사전순으로 정렬한다.
  - 위치마다 종류, 경로 또는 `패키지 버전 (state 앞 8자리)`, 다를 때만 파일 이름, 키음 `있음/필요`, BGA를 보여준다.
  - 차이 요약을 한 줄로 적는다 (예: "리소스 차이 있음", "파일 이름 다름").
  - 중복 종류를 구분한다: `폴더+패키지`(설치 연결, 의도한 경우가 많음)와 `폴더×N`(실수일 가능성이 높음).
  - 게임이 실제로 로드할 위치는 내부 규칙으로 정한다: "리소스가 온전한 위치 중 정렬상 첫 번째". 이 규칙은 화면에 대표로 표시하지 않지만 `bpm song`에 로드 위치로 한 줄 명시한다. 사용자가 로드 위치를 바꾸고 싶으면 `set-primary`가 아니라 `bpm song prefer <위치>` 같은 선택 기능으로 둔다(후속 단계).
- `bpm status`는 한 번에 요약한다: 출처 수, 차트 수, 곡 수, 중복 그룹 수, 패키지 설치 수, 난이도표 연결률.
- 기존 명령(`install`, `import`, `export`, `library`, `table`)은 그대로 유지한다. 새 명령은 기존 함수를 호출하는 얇은 층이다. 호환을 깨지 않는다.

### 온라인 허브 (신규 요구)

예전에는 BMS 저장소가 거의 없어서 사용자가 곡을 직접 찾아 모아야 했다. 지금은 미러와 정리된 사이트가 많으므로, BPM이 온라인 허브를 조회할 수 있게 한다.

- **허브는 어댑터로 추가한다.** 허브마다 조회 방식이 다르므로, 공통 인터페이스(해시로 조회, 곡 검색, 차분 목록 가져오기) 뒤에 허브별 구현을 둔다. 기존 원격 레지스트리(`bpm search`, `bpm install <id>`)의 설정 방식을 따른다.
- **첫 번째 허브 후보는 BMS SEARCH(`bmssearch.net`)다.** 검색 결과에 공식 API가 있고, 譜面 파일의 SHA-256을 보내면 같은 본체로 보이는 譜面 목록을 돌려준다는 설명이 있다. 다만 API 문서(`bmssearch.stoplight.io/docs/bmssearch-api`)를 자동 조회하지 못했다. **엔드포인트, 파라미터, 응답 형식, 사용 제한은 구현 전에 직접 확인해야 한다.** 웹 페이지(`/search?q=`, `/bmses/...`)만으로 역공학해 구현하지 않는다.
- **다른 미러는 아직 확정하지 않았다.** 조사에서 2025~2026년 기준으로 살아 있는 채보 미러를 확인하지 못했다. 허브 목록은 설정 파일로 두고, 사용자가 추가할 수 있게 한다.
- **할 수 있는 일**
  - 로컬 `ChartId`로 온라인에서 같은 譜面를 찾는다 (온라인 존재 확인).
  - 한 곡의 차분 중 내게 없는 것을 찾는다 (누락 차분 목록). 이 목록은 Song 묶음과 함께 보여준다.
  - 같은 본체의 다른 版(같은 곡의 다른 바이트)을 찾는다. 이때 바이트가 다르므로 `ContentKey` 없이는 같은 차트로 단정하지 않는다.
- **하지 않는 일**: 조회 결과를 자동으로 내려받지 않는다. 다운로드는 `bpm online get <…>`처럼 명시적으로 요청할 때만 하고, 받은 파일은 검증(해시 확인) 후 기존 설치 경로로 넘긴다. 허브가 준 파일은 신뢰하지 않는 입력으로 취급한다.
- **네트워크 위치**: 호출은 `bms-package-manager`에 두고, 앱(`beetle-app`)은 네트워크를 쓰지 않는다. HTTP는 이미 쓰는 `ureq`를 재사용하고 새 크레이트를 추가하지 않는다.
- **예의**: 응답을 캐시하고, 요청 간격을 두며, 허브가 요구하는 사용 조건(공개 API 사용 범위, 출처 표기)을 따른다.

## 5. CLI 명령 구조 (제안)

새 명령을 중심으로 하고, 기존 명령은 "고급" 섹션으로 내린다.

```text
bpm status                         전체 요약
bpm scan [--full]                  등록된 출처를 스캔해 인덱스를 갱신
bpm songs [필터...]                곡 목록 (차분 수, 모드, 위치 요약)
bpm song <id|제목>                 한 곡의 차분 상세
bpm charts [필터...]               차트 목록 (ChartId 앞 16자리 표시)
bpm dupes                          바이트 동일 중복 그룹
bpm delete <경로|ChartId>          한 항목 삭제 (휴지통 이동, 확인 문자열 필요) — 후속 단계
bpm online hubs                    등록된 온라인 허브 목록
bpm online find [경로|ChartId...]  온라인 허브에서 같은 譜面 찾기
bpm online missing <Song>          한 곡의 누락 차분 찾기
bpm sources                        등록 출처 목록 (library + packages)
bpm sources add|remove <경로>      출처 추가/제거 (library 명령의 새 이름)
bpm tables ...                     기존 bpm table 유지
```

- 기존 `bpm library ...`는 `bpm sources ...`의 별칭으로 남긴다.
- 인덱스는 `scan`이 만들고, 나머지 조회 명령은 인덱스만 읽는다. 조회가 매번 전체 파일을 해시하지 않게 한다.
- 인덱스 파일은 기존 TSV 캐시 형식을 확장한다. 새 JSON/DB 의존성은 도입하지 않는다(AGENTS.md §3).

## 6. 구현 순서

1. `bms-hash` 크레이트 추출 및 `ChartId` 계산을 스캔 경로에 연결 (이미 `identity.rs`에 있음, 연결만 한다)
2. 인덱스 파일 형식 확장: `ChartId`, MD5, Location 목록, Song 묶음 키
3. `bpm scan` / `bpm status` / `bpm sources`
4. `bpm dupes` (목록만)
5. `bpm songs` / `bpm song` / `bpm charts` 질의와 필터
6. 난이도표 레벨을 질의 필터에 연결 (표 설계와 합침)
7. 기존 명령을 새 구조 아래로 정리하고 도움말 개편

각 단계는 커밋 하나로 끝나게 나눈다. 단계 3까지가 "사용자가 처음 체감하는 최소 가치"다.

## 7. 결정이 필요한 사항

구현 전에 사용자가 정해야 하는 것은 다음 세 가지다.

1. **Song 묶음 기준**: §3 우선순위와 §3.1 정규화 규칙을 승인할지. 특히 3단계는 키음 겹침 조건을 필수로 할지 확정이 필요하다.
2. **삭제 정책**: 사용자 요청 시에만, 한 번에 한 항목, 휴지통 이동 기본, `--purge`와 확인 문자열 요구로 정했다. 이 방향이 맞는지 확인이 필요하다.
3. **기본 표시**: 대표 위치 없이 병합 표시하고, 로드 위치는 내부 규칙으로 정한다. 이 방향이 맞는지 확인이 필요하다.
4. **온라인 허브**: BMS SEARCH API 명세를 확인한 뒤 구현 범위를 정한다. 다른 미러는 아직 확정되지 않았다.

### 3.1 Song 묶음 기준 검토 결과

Opus 검토(2026-10-09) 결과를 요약한다. 자동 묶기는 보수적으로 하고, 애매하면 사용자에게 묻는다.

- **정규화 키 v1** (정규식 없이 문자 단위 처리, 결정론 유지)
  1. 전각 ASCII(U+FF01–FF5E)를 반각으로, U+3000은 공백으로. `【】〔〕`는 `[]`, `～〜`는 `~`, `‐–—−`는 `-`로 바꾼다. 고정 표 하나로 처리하고 NFKC 크레이트는 쓰지 않는다.
  2. 소문자화는 ASCII만 한다. 유니코드 대소문자 표는 Rust 버전에 따라 달라질 수 있어 쓰지 않는다.
  3. 연속 공백을 하나로 줄이고 앞뒤를 자른다.
  4. 차분 표기를 제거한다. 기존 `canonicalize_title`([pack.rs](../../crates/bms-package-manager/src/pack.rs))를 재사용하고, 전각 괄호 처리와 끝의 `-ANOTHER-`, `~HYPER~` 같은 구분자 표기 제거, `light`, `black`, `kai`, `ex` 토큰을 보강한다. 실제 제목 단어를 지우지 않도록 대괄호·괄호 안이나 구분자로 감싼 끝부분에서만 지운다.
  5. `#SUBTITLE`은 키에 넣지 않는다. 다만 차분 토큰이 아닌 부제가 서로 다르고 키음도 겹치지 않으면 자동 묶기를 하지 않는다.
  6. 아티스트 기본 키는 첫 ` obj`, `(obj`, `/obj`, ` / ` 앞까지만 쓴다.
  7. 곡 대표 제목과 아티스트는 **서로 다른 ChartId 단위**로 다수결한다. 위치 수로 세면 중복 복사본이 표를 왜곡한다. 동률은 사전순으로 작은 값이 이긴다 (`pick_most_common` 재사용).
- **키는 재생성 가능한 인덱스 캐시에만 둔다.** 규칙이 바뀌면 `key_v`를 올리고 재스캔한다. 사용자 지정 묶음은 ChartId로 저장하므로 규칙이 바뀌어도 깨지지 않는다.
- **사용자 확인이 필요한 경우**: 3단계 후보, 과반이 근소한 폴더(약 50–66%), 정규화 뒤 제목 키가 비어 원래 제목으로 돌아간 경우.
- **주요 위험**: 흔한 제목("Destination", "Snow")의 다른 곡이 잘못 묶이는 것. 키음 겹침 조건과 확인 절차로 줄인다. 반대로 키음 파일 이름을 바꾼 재배포판은 자동으로 묶이지 않고 후보로만 남는다.
- **연쇄 병합 주의**: 여러 곡을 몰아넣은 폴더에서 차트 하나가 공유되면 큰 묶음이 연쇄로 합쳐질 수 있다. 몰아넣은 폴더를 먼저 키별로 나눈 뒤 union을 해야 한다.
- **정규화 범위의 한계**: ASCII와 전각만 다룬다. 반각 가타카나와 한글 자모 조합형은 같은 문자로 보지 않으므로 후보 확인에 맡긴다.
- **출력 ID 안정성**: `song:` ID는 구성원이 바뀌면 바뀔 수 있다고 출력에 명시한다.

§7의 네 항목에 대한 결정이다. 앞의 본문과 충돌하면 이 절이 우선한다.

### 9.1 Song 묶음 (§3, §3.1 승인)

- 3단계(폴더 사이 묶기)는 **키음 겹침 확인을 필수**로 한다.
- 비교 대상은 `#WAVxx` 파일 이름의 **확장자 없는 stem**(경로 구분자 `\`→`/`, ASCII 소문자화)이다. 재배포판의 `.wav`→`.ogg` 변경을 허용하기 위해서다.
- 자동 묶기 조건(둘 중 하나):
  - Jaccard ≥ 0.5이고 교집합 ≥ 8
  - |A∩B| / min(|A|,|B|) ≥ 0.9이고 작은 쪽 집합 ≥ 16
- 이름이 숫자나 2자리 base36뿐인 것(`01`, `0a`, `001`)이 과반이면 판정하지 않고 후보로만 둔다.
- 수치(0.5, 8, 16, 0.9)는 실측이 아니다(미확인). `key_v`에 묶어 두고 바꾸면 재스캔한다.
- **CLI 1단계 영향**: 인덱스에 차트마다 정규화 stem 목록(정렬)과 `key_v`를 넣는다. `bpm status`의 곡 수는 5단계 전까지 `-`로 둔다.

### 9.2 삭제 정책 (§2 승인, 세부 확정)

- 휴지통은 **해당 파일이 속한 출처 루트 안의 `.bpm-trash/`**다. BPM 데이터 디렉터리와 Windows 휴지통은 쓰지 않는다.
  - 경로: `<출처 루트>\.bpm-trash\<UTC 시각>-<ChartId 앞 16자리>\<원래 상대 경로>`
- 이동은 `std::fs::rename`만 쓴다. 실패하면 중단한다. 복사 후 삭제로 대신하지 않는다.
  - 근거: 같은 볼륨 안에서만 즉시 원자적이다. BPM 데이터 디렉터리에 두면 컬렉션이 외장 드라이브에 있을 때마다 드라이브 간 이동이 된다.
- 한 번에 **차트 파일 하나**만 지운다. 폴더 단위 삭제는 범위 밖이다.
- ChartId로 지정했을 때 같은 ChartId의 폴더 위치가 2개 이상이면 거부하고 경로로 다시 지정하게 한다.
- `packages/` 아래와 `.bpm-trash/` 아래 경로는 거부한다. 마지막 사본을 지울 때는 "마지막 사본" 경고를 따로 표시한다.
- 확인 문자열 16자는 `ChartId::short()` 출력을 그대로 입력하는 형식이다.
- **CLI 1단계 영향**: `bpm delete`는 구현하지 않는다. `scan`은 `.bpm-trash/`를 처음부터 건너뛴다. 인덱스의 각 위치에 **출처 ID(출처 루트)**를 기록한다.

### 9.3 기본 표시와 로드 위치 (§4 P4 승인, 규칙 확정)

- **온전한 위치**: 모든 `#WAV`가 확장자 대체 규칙을 포함해 실제 파일로 찾아지는 위치다. BGA 유무로 탈락시키지 않는다.
- **로드 규칙**: 온전한 위치 중 P4의 정렬 순서(종류 → 경로 또는 패키지 ID → 버전)로 첫 번째를 쓴다. 온전한 위치가 없으면 정렬상 첫 위치를 쓴다.
- 이 규칙은 `beetle-core`의 **순수 함수 하나**에 둔다. bpm과 게임이 같은 함수를 호출한다.
- `bpm song`에는 위치 목록 아래 한 줄로 표시한다.
  - `로드: <위치> (온전한 위치 중 첫 번째)`
  - `로드: <위치> (온전한 위치 없음: 키음 N개 누락)`
  - 목록 안에 대표 표시(`*`)는 두지 않는다.
- 패키지 버전 정렬은 숫자 구간 단위로 할지 구현할 때 정한다(문자열 정렬은 `1.10 < 1.9`가 된다).
- **CLI 1단계 영향**: `scan`은 위치마다 **누락 키음 수**를 기록한다. `bpm dupes`는 그룹마다 로드 위치 한 줄을 보여준다.
- 미확인: 현재 `beetle-app`이 중복 ChartId 중 어느 위치를 로드하는지는 코드에서 확인하지 않았다.

### 9.4 온라인 허브 (BMS SEARCH)

- **1단계에서 제외한다.** 네트워크 코드는 넣지 않는다.
- 공식 API 문서 사이트(`bmssearch.stoplight.io`)는 현재 "Workspace does not exist"로 접근되지 않는다. 공식 note 글에는 엔드포인트 명세가 없고, 사용 조건은 "특별한 클라이언트 제한은 없으니 양식 있는 범위에서 이용"이라는 한 문장뿐이다. 요청 한도와 출처 표기 조건은 확인하지 못했다(미확인).
- 직접 요청으로 확인한 동작(문서로 확인한 것이 아님):
  - `GET https://api.bmssearch.net/v1/patterns/sha256/{sha256}`: 실제 해시면 200(譜面와 `bms.id`), 없으면 404
  - `GET https://api.bmssearch.net/v1/bmses/{id}/patterns`: 200(譜面 배열, `file.hashSha256` 포함)
  - 검색(`bmses/search`)과 다운로드(`downloads[].url`)는 제외한다.
- **후속 단계의 최소 범위**: 위 GET 두 개만 쓴다. 각각 `online find`와 `online missing`에 해당한다. 기존 `ureq`를 재사용하고, User-Agent에 `bpm/<버전>`을 넣는다. 요청 사이 최소 1초 간격을 두고, 사용자가 명시한 ChartId만 조회한다. 응답은 TTL 있는 로컬 캐시에 둔다. 스키마가 예상과 다르면 실패로 처리하고 추정하지 않는다.
- **구현 전 조건**: 현행 API 문서를 확보하거나 운영자에게 사용 확인을 받는다. 추정 경로로만 확인했으므로 "역공학으로 구현하지 않는다"는 원칙(§4 온라인 허브)에 아직 걸린다.
- **CLI 1단계 영향**: 인덱스에 ChartId 64자 전체를 저장한다. 이것이 나중의 조회 키가 된다. 추가 작업은 없다.

### 9.5 CLI 1단계 확정 범위 요약

인덱스에 다음을 넣는다: ChartId(64자), MD5, 위치마다 출처 ID·종류·경로·누락 키음 수, 정규화 stem 목록(정렬)과 `key_v`. `scan`은 `.bpm-trash/`를 건너뛴다. 구현 순서는 §6의 1–4단계다.

### 9.6 리뷰 후속 결정 (2026-10-09, Opus)

**Q3. `loads:` 줄과 게임이 여는 사본**

- 결정: 게임도 `beetle_core::choose_load_index`를 같은 배치 순서로 쓰게 하는 것이 목표다. 단, 게임 변경은 이번 마일스톤(bpm CLI 1–5단계)에 넣지 않고 다음 별도 마일스톤으로 둔다.
- 이유: 게임의 스캔 순서는 `read_dir` 결과를 정렬하지 않으므로 bpm이 결정론적으로 재현할 수 없다. 출처도 `songs/`, `packages/`, library, `BMS_DIR` 순으로 고정되어 있어 bpm의 출처 목록과 다르다.
- 이번 마일스톤의 처리: `loads:` 줄에 "the game does not follow this rule yet"을 붙인다. `load_location.rs`의 주석은 현재 bpm만 쓴다고 고쳤다.
- 다음 마일스톤의 범위: 출처 목록(`library.dat`, 기본 `songs/`, `BMS_DIR`)을 공유 함수 하나로 만들고, 게임은 설치된 state를 패키지 출처로 쓴다. `dedup_songs`는 `(kind, source, path)` 순으로 정렬한 뒤 `choose_load_index`를 호출한다. 온전성 계산은 사본이 2개 이상인 ChartId에만 한다. `songs.cache`는 버전을 올려 무효화한다.
- 사용자 확인 필요: 기존 중복 차트가 다른 사본에서 열리는 것을 받아들일지, `BMS_DIR`와 개발용 경로(`target/release/packages`, `../packages`)를 정식 출처로 남길지.

**Q6. 폴더 과반 규칙**

- 결정: 과반 규칙을 구현한다. 근소한 과반일 때 확인 단계는 두지 않는다. 대신 `Song::candidates`가 확인 역할을 맡는다.
- 알고리즘(Rule 1):
  1. 위치(kind, source, 디렉터리)마다 그 위치의 서로 다른 ChartId를 모은다.
  2. 제목 키가 가장 많은 그룹을 기준(anchor)으로 한다. 동률이면 사전순으로 작은 제목. `기준 수 × 2 ≥ 위치의 차트 수`일 때만 기준이 있다.
  3. 기준 그룹은 같은 제목끼리 차례로 묶는다.
  4. 나머지 차트 O는 `|O∩A| ≥ 4`이고 `|O∩A| × 10 ≥ |O| × 8`일 때만(A는 기준 그룹 stem의 합집합) 기준 그룹에 합류한다. 조건에 맞지 않으면 기준 곡과 후보 쌍으로 표시한다.
  5. 이상치끼리는 서로 묶지 않는다(연쇄 병합 방지). 분리 지정은 모든 합류에서 존중한다.
  6. 기준이 없으면(여러 곡을 몰아넣은 위치) 같은 제목끼리만 묶는다.
  7. 일련번호 가드(`mostly_serial`)는 위치 안 규칙에는 적용하지 않는다. 같은 폴더의 차분은 같은 파일을 쓰기 때문이다.
- 수치(0.5, 4, 0.8)는 실측값이 아니다(미확인). 곡은 조회 시 계산되므로 재스캔 없이 바꿀 수 있다.
- 검증: `songs.rs`의 `place_rule_tests`(기준 있음·없음, 키음 불일치 후보, 일련번호 이름)로 확인했다.
- 설계 §3 Rule 1과 §3.1의 "근소한 과반 확인" 항목은 이 결정으로 대체된다.

### 9.7 게임 로드 위치 통일 (완료)

- 게임 스캐너(`beetle-app/src/scanner.rs`)가 bpm과 같은 출처 목록(`collection_folders`: library, `songs/`, `BMS_DIR`)을 쓰고, 활성 패키지 state만 읽습니다(`bms_package::installed`).
- 같은 ChartId의 사본은 `(kind, source, path)` 순으로 정렬한 뒤 `choose_load_index`로 하나를 고릅니다. 온전성(누락 키음)은 사본이 둘 이상인 ChartId에만 계산합니다(`beetle_core::key_sounds`).
- 사용자 결정: 레지스트리에 없는 `packages/`의 `.bmsp`는 게임 목록에서 뺍니다. 개발용 패키지 경로(`target/release/packages`, `../packages`)는 스캔하지 않습니다.
- `songs.cache`는 `#BEETLE_SONGS_V5`로 올렸고, `registry.json`이 캐시보다 새로우면 다시 스캔합니다.
- 결과로 일부 중복 차트는 예전과 다른 사본에서 열릴 수 있습니다. 사용자가 수용했습니다.
- 검증: `beetle-app` scanner 테스트 5개(교차 검증 `game_and_bpm_choose_the_same_copy` 포함)와 전체 워크스페이스 테스트 통과. 게임 실행 확인은 아직 하지 않았습니다(아래 수동 확인).
