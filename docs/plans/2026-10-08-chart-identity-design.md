# Chart Identity 설계 (2026-10-08)

[chart resolver 계획](2026-10-07-chart-resolver-identity-and-library.md)의 Phase B를 구체화한다. 점수 기록 설계([score record 설계](2026-10-07-score-record-design.md))가 키를 불투명한 문자열로 저장하도록 만들어 두었으므로, 이 문서는 그 키가 무엇인지를 정한다. 구현 전 설계다.

## 현재 상태와 문제

차트 식별자는 `SongMetadata::hash`(`u64`)다. [library.rs](../../crates/beetle-core/src/library.rs)의 `compute_chart_hash`가 **디코딩한 텍스트**(`decode_bms_text` 결과)의 UTF-8 바이트에 FNV-1a 64비트를 건다.

| 문제 | 설명 |
|---|---|
| 외부 생태계와 맞지 않음 | BMS 난이도표와 LR2·beatoraja 점수 DB는 차트를 파일 바이트의 MD5 또는 SHA-256으로 가리킨다. FNV 64비트로는 어느 것과도 연결할 수 없다. |
| 디코더에 의존 | 해시가 파일 바이트가 아니라 디코딩 결과에 걸린다. Windows에서는 CP932 → CP949 → ANSI 순으로 시도하고 다른 OS에서는 손실 UTF-8로 떨어지므로, 같은 파일이 환경에 따라 다른 키를 얻을 수 있다. 기록 파일을 다른 컴퓨터로 옮기면 어긋난다. |
| 64비트 | 수만 개 규모의 Library에서는 충돌 확률이 무시할 수 없다. 충돌하면 두 차트가 기록 하나를 공유한다. |
| 비용 | 위 문제들 때문에 키를 바꾸는 일은 곡이 늘수록 비싸진다. 기록, 리플레이, 캐시가 모두 이 키에 묶여 있다. |

키가 쓰이는 곳:

| 위치 | 용도 |
|---|---|
| `ScoreStore` (`scores.dat`) | 기록의 키 |
| `replays/<16자리 16진>.rep` | 리플레이 파일 이름과 헤더 `hash=` |
| 아트워크 캐시 `<16자리 16진>.bmp` | 스테이지 이미지 캐시 파일 이름 |
| 곡 목록 캐시 (TSV 첫 열) | 곡 메타데이터 |
| 화면 상태 | 스테이지 이미지 캐시, 미리듣기, 선택 곡 비교 등 메모리 안의 키 |

패키지 시스템에는 이미 SHA-256이 있다 (`bms-package`의 `checksum.rs`, 델타의 `base_hash`·`target_hash`, 패키지 `state_hash`).

## 확정된 결정 (사용자 선택)

1. **기본 키는 원본 파일 바이트의 SHA-256**이다. 난이도표와 beatoraja가 쓰는 방식과 같다.
2. **MD5도 함께 계산해서 곡 목록 캐시에 저장한다.** 난이도표 대부분이 MD5로 차트를 가리키므로 외부 호환 별칭으로 쓴다. 키로는 쓰지 않는다.

## 모델

```text
ChartId  = SHA-256(원본 파일 바이트)       32바이트. 키.
md5      = MD5(원본 파일 바이트)           16바이트. 외부 호환 별칭. 키가 아님.
```

- **정규화를 하지 않는다.** 해시는 디코딩, 줄바꿈 정리, 대소문자 정리 없이 파일 바이트 그대로에 건다. 그래서 정규화 규칙의 버전 관리가 필요 없고, 규칙을 바꿔서 모든 키가 무효가 될 위험이 없다. (이전 계획에 있던 `canonicalization version`은 이 결정으로 필요 없어졌다.)
- **같은 파일이면 같은 차트다.** 어느 패키지, 어느 폴더에 있어도 바이트가 같으면 ID가 같다. 이것이 처음 요구한 "다른 패키지에 설치해도 같은 차트로 인식"이다.
- **인코딩이나 줄바꿈만 다른 복사본은 다른 차트다.** LR2·beatoraja와 같은 동작이고, 난이도표와도 이렇게 맞는다. 의미상 같은 차트를 묶는 일은 별도 개념으로 나중에 한다 (아래).
- **`#RANDOM` 차트**의 ID는 원본 파일의 ID다. 굴림은 ID가 아니라 플레이 속성이고, 시드는 이미 기록 스냅샷과 리플레이에 들어간다.
- **표기**: `sha256:<소문자 16진 64자>`. 파일 이름과 화면에서는 앞 16자(64비트)로 줄여 쓰고(`short()`), 같은지 비교할 때는 항상 전체를 쓴다.
- **출처는 ID에 넣지 않는다.** 폴더 경로, 패키지 ID, 패키지 `state_hash`, 패키지 안 항목 경로는 `SongMetadata::file_path`(`패키지::항목` 형태)와 이후 Library가 따로 기억한다. 같은 ID가 여러 출처에 있을 수 있다.

### 의미상 같은 차트 (지금은 구현하지 않음)

바이트는 다르지만 같은 차트인 경우(오타 수정, 재인코딩)를 묶는 `ContentKey`가 Library 단계에서 필요하다. 디코딩 + 줄바꿈 정규화 + 버전 태그로 정의할 수 있고, **점수 키로는 쓰지 않는다**. 중복 분석("같은 차트 / 다른 바이트")과 점수 이전 제안에만 쓴다. 정규화 규칙의 버전은 그때 정한다.

## 구현 구조

- **해시 구현의 위치**: SHA-256은 `bms-package/src/checksum.rs`에 이미 있고(외부 크레이트 없이 214줄), beetle-core도 필요하다. 패키지 크레이트가 플레이어 코어에 의존하게 만들지 않기 위해 **작은 내부 크레이트 `bms-hash`**를 만들어 SHA-256을 옮기고 MD5를 추가한다 (외부 의존 없음, 둘 다 `bms-hash`에 의존). 새 외부 크레이트는 도입하지 않는다 (AGENTS.md §3). `AGENTS.md` §4의 모듈 목록에 한 줄 추가한다.
- **`ChartId` 타입** (beetle-core): `[u8; 32]`을 감싼 `Copy + Eq + Hash` 값. `Display`와 `FromStr`로 `sha256:` 표기를 다루고, `short()`는 파일 이름용 16자리다.
- **계산 시점**: 곡 목록 스캔 때 파일을 읽을 때 한 번 (바이트를 이미 읽는다). 패키지 안 차트는 항목을 읽을 때 같은 바이트 기준이다. 해시 비용은 8MB짜리 차트에서도 수십 ms 안쪽이라 스캔 시간에 영향이 작다.
- **`SongMetadata`**: `hash: u64`를 `id: ChartId`로 바꾸고 `md5`를 추가한다. 마이그레이션 동안만 `legacy_hash: u64`(기존 FNV)를 함께 들고 있는다.

## 데이터 형식 변경

| 대상 | 변경 |
|---|---|
| 곡 목록 캐시 | 헤더 `#BEETLE_SONGS_V2`와 `필드=값` 형식으로 바꾸고 `id`, `md5`, `legacy`를 넣는다. 옛 캐시는 읽지 않고 한 번 전체 재스캔한다 (캐시는 다시 만들 수 있다). |
| 점수 파일 | `chart=sha256:<64자>`. 옛 키(`chart=<16자리 16진>`)는 `legacy` 키로 읽는다. |
| 리플레이 | 헤더 `hash=` 줄은 그대로 읽고(옛 파일), 새 파일은 `chart=sha256:<64자>`를 쓴다. 파일 이름은 `<short>.rep`. |
| 아트워크 캐시 | `<short>.bmp`. 마이그레이션 없이 다시 만든다 (캐시이므로). |

## 마이그레이션

기존 기록과 리플레이는 FNV 키로 저장되어 있다. 스캔이 `legacy_hash`와 `id`를 함께 계산하므로 그 대응으로 옮긴다.

1. 곡 스캔 직후 `ScoreStore::migrate(&[(legacy_hash, id)])`가 옛 키 기록의 키를 새 ID로 바꾼다.
2. 곡 목록에 아직 없는 차트의 기록은 옛 키로 남는다. 그 차트가 나중에 스캔되면 그때 옮겨진다. 기록은 버려지지 않는다.
3. 같은 `legacy_hash`가 서로 다른 ID 둘 이상에 대응하면(디코딩 결과는 같고 바이트는 다른 복사본, 예: Shift-JIS와 UTF-8) 기록을 **각 ID로 복사**한다. 사용자가 플레이한 것이 어느 쪽이든 같은 차트였기 때문이다.
4. 리플레이 파일(`<옛 16자리>.rep`)은 대응이 풀리는 시점에 `<short>.rep`로 이름을 바꾼다.
5. 첫 마이그레이션 전에 점수 파일을 한 번 더 백업한다 (`scores.dat.v2.bak`, 이미 있으면 덮어쓰지 않는다).

## 단계

1. **`bms-hash` 크레이트와 `ChartId`** (완료): SHA-256 이동, MD5 추가, 표준 시험 벡터 테스트, `ChartId`, `SongMetadata`와 곡 목록 캐시 V2. 점수와 리플레이 키는 아직 옛 값을 쓰도록 `legacy_hash`를 병행한다.
2. **키 교체와 마이그레이션** (완료): `ScoreStore`, 리플레이, 화면 상태의 키를 `ChartId`로 바꾸고 `migrate`를 구현한다. 실제 `scores.dat` 사본으로 25개 기록이 모두 옮겨지는지 확인한다.
3. **파일 이름과 검증**: 리플레이와 아트워크 캐시의 파일 이름, 그리고 외부 값과의 대조 검증.

단계 1에서는 로컬 BMS 폴더의 차트 602개(43MB)에 대해 `ChartId`와 MD5가 파이썬 `hashlib` 결과와 모두 일치하는 것을 확인했다. SHA-256과 MD5를 함께 계산하는 속도는 약 140MB/s(코어 예제, 릴리스 프로파일)라서 곡 목록을 처음 스캔할 때만 비용이 들고 캐시가 있으면 들지 않는다. 구현에서 정한 것: `SongMetadata`는 `id`, `md5`와 함께 옛 FNV 키를 `hash` 필드에 그대로 두어(단계 2에서 `legacy_hash`로 바꾼다) 점수·리플레이·캐시가 아직 옛 키로 동작한다.

단계 2에서는 `ScoreRecord`와 리플레이가 `ChartKey`(`Id` 또는 `Legacy`)를 쓰고, `ScoreStore::migrate`가 옛 키 기록을 id로 옮긴다. 실제 `scores.dat` 사본(기록 25개)을 로컬 곡 목록(패키지 149곡 + 폴더 602곡)으로 옮겼을 때 23개가 옮겨졌고, 데모 곡 기록을 포함하도록 고친 뒤에는 24개가 대응된다. 남은 1개는 목록에 없는 차트의 기록이라 그 차트가 나타날 때까지 옛 키로 남는다. 점수 파일은 처음 옮기기 전에 `scores.dat.pre-id.bak`으로 백업한다. 리플레이 파일은 옛 이름 그대로 두고 새 이름으로 복사한다 (옛 파일은 지우지 않는다). `SongMetadata::hash`는 `legacy_hash`로 이름을 바꿨고, 마이그레이션 대응 외에는 쓰이지 않는다.

## 외부 값 대조 결과 (2026-10-08)

Satellite 난이도표(`score.json`, 차트 2,467개, 항목마다 `md5`와 `sha256`)와 로컬 차트의 해시를 비교했다.

| 대상 | 차트 수 | MD5가 표에 있음 | SHA-256이 표에 있음 | 같은 항목을 가리킴 |
|---|---|---|---|---|
| 폴더의 차트 파일 | 602 | 15 | 15 | 15 |
| 패키지(`.bmsp`) 안의 차트 | 149 | 11 | 11 | 11 |

- 두 값 모두 **표의 항목과 정확히 일치**했고, 한 쪽만 맞거나 두 값이 서로 다른 항목을 가리킨 경우는 한 건도 없었다. 파일 바이트의 SHA-256과 MD5가 난이도표와 같은 식별자라는 가정이 확인됐다.
- 패키지 안 차트의 해시도 표와 일치했으므로, 확인한 11개에서는 패키저가 차트 바이트를 바꾸지 않았다.
- 표에 없는 차트는 Satellite가 다루지 않는 곡이다 (표가 다루는 곡만 맞는다).
- 이 대조는 LR2 점수 DB(MD5)와 beatoraja(SHA-256)가 쓰는 값이 같다는 것까지 확인한 것은 아니다. 난이도표가 두 값을 모두 파일 바이트 기준으로 싣는다는 점만 확인했다.

## 위험과 검증

- **외부 값과의 일치는 구현 때 대조로 확인해야 한다.** LR2는 파일 바이트의 MD5, beatoraja는 파일 바이트의 SHA-256을 쓴다고 알고 있지만 이 저장소에서 확인하지 못했다. 단계 3에서 난이도표 하나의 MD5/SHA-256 항목을 로컬 차트와 비교한다.
- **패키지 안 차트의 바이트가 원본과 같은지**: 패키저가 차트 파일을 다시 쓰지 않고 그대로 넣는지 구현 때 확인한다 (`bpm pack`이 차트 텍스트를 분석용으로만 읽는 것은 코드에서 확인했다). 바이트가 달라지면 같은 곡의 폴더판과 패키지판이 다른 ID를 얻는다.
- **차트가 조금 고쳐진 새 판**은 새 ID가 된다. 이전 판의 기록은 이전 ID에 남는다. 두 판을 잇는 일은 `ContentKey`(Library 단계)의 몫이다.
- **MD5는 충돌 저항이 없다.** 외부 별칭으로만 쓰고, 두 차트가 같은지는 항상 SHA-256으로 판단한다.
- **데모 곡**(`:demo:`)은 파일이 없으므로 고정 문자열의 SHA-256으로 ID를 만든다.
